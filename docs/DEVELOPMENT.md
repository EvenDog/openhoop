# Developing OpenHoop

How the code is laid out, how to build and test it, and what the tests cover. For an overview, see the [README](../README.md).

## Build and test

Requires Xcode's Swift toolchain, Python 3, and an Apple Silicon Mac. Dependencies are pinned in `requirements-build.txt` and installed into the project-local `.venv`.

```sh
./scripts/build.sh
./scripts/test.sh
```

To pack the built app into a DMG for downloading, run `./scripts/make-dmg.sh`. It works on a copy, so an open copy of the app is left alone. Set `SIGN_IDENTITY` to a Developer ID Application certificate to sign it with the hardened runtime, and `NOTARY_PROFILE` to credentials saved with `xcrun notarytool store-credentials` to have Apple notarize it and staple the result, so it opens on other Macs without a warning:

```sh
SIGN_IDENTITY="Developer ID Application: …" NOTARY_PROFILE=openhoop-notary ./scripts/make-dmg.sh
```

The app updates itself with [Sparkle](https://sparkle-project.org) 2 (`Sources/EmbroideryApp/Updates.swift`): it reads the feed at `https://openhoop.app/appcast.xml` (`website/appcast.xml`) once a day, and only installs downloads signed with the update key whose public half is `SUPublicEDKey` in `Resources/Info.plist`. The private key lives in the release maker's login keychain under the account `openhoop` (made once with Sparkle's `generate_keys --account openhoop`; back it up with `generate_keys --account openhoop -x <file>`, since without it no update can be signed). To release a version:

1. Raise `CFBundleShortVersionString` and `CFBundleVersion` in `Resources/Info.plist` (Sparkle compares `CFBundleVersion`, so it must go up every time).
2. Build, then make the signed, notarized DMG as above.
3. Publish the GitHub release `v<version>` with the DMG and the release notes (Markdown).
4. `python3 scripts/add-to-appcast.py dist/OpenHoop-<version>.dmg <notes.md>` signs the DMG and adds it to `website/appcast.xml`; publish that, with the website's download links, by PR. Once the site deploys, every copy with the updater offers the new version.

`build.sh` copies the bundled embroidery fonts (`Resources/EmbroideryFonts`, downloaded unmodified by `scripts/fetch-embroidery-fonts.sh` from a pinned commit of the Ink/Stitch font collection) and builds the native app in optimized (release) mode, which generates large fills about 40 times faster than a debug build, packages the converter with PyInstaller, and signs and verifies the app locally. The initial dependency installation requires network access. `test.sh` expects the virtual environment created by the build.

`Sources/EmbroideryCore` contains the millimeter geometry, running, satin and fill generators, project model and shortcut registry. `Sources/EmbroideryApp` contains AppKit document/window management and drawing, SwiftUI panels, and export orchestration. `Sources/GeometryBridge` vendors Clipper2 2.0.1 for polygon offsetting. `Helper` contains the versioned converter protocol and PES tests.

Build the app before running the tests: native format integration exercises the actual bundled helper.

Two tests look at the engine as a whole. `SavedProjectsTests` opens every project in `docs/sewout` and `dist`, checks that each saves and reopens unchanged, and sews it. `RandomDesignTests` is a seeded crash hunt: random shapes, settings and node edits. It checks that the engine never crashes, never sews a stitch over 12.1 mm or far outside its shape, that the node-drag check agrees with the engine, and that cached stitches match fresh ones. The normal suite runs 15 rounds. For a long hunt, use a release build:

```sh
FUZZ_ROUNDS=5000 FUZZ_SLOW=1 FUZZ_OUT=/tmp/hunt swift test -c release -Xswiftc -enable-testing --filter RandomDesignTests
```

`FUZZ_SLOW` also reports objects that take longer than that many seconds to stitch, `FUZZ_OUT` saves each problem round's design, and `FUZZ_SEED=<n>` replays one round.

## Project files and settings

- **File versions.** Projects are saved as schema 4, or schema 5 once anything needs newer features: Bézier handles, start/end points, closed or font satins, fill styles, bean stitch, short stitches or split satin, or cut-out overlaps. Older app versions then refuse the file instead of silently dropping that data. Schema 1–4 projects still open, and objects without those features generate exactly the same stitches as before.
- **Stitch engine version.** A project saved by an older engine (such as `digitize-2`, before travel runs) shows its saved stitches as a preview until you choose **Regenerate with current engine** in the Design panel.
- **Settings** (shortcuts, panel layouts, view, hoop and fabric choices) live in `~/Library/Application Support/Embroidery/preferences.json`; imported thread charts in `~/Library/Application Support/Embroidery/ThreadCharts`. The folder keeps its pre-rename name so existing settings carry over.
- **Fill section order.** A fill split into sections (around holes and concave parts) sews them in a travel-saving order: after each section the needle goes to the remaining section it can reach by the shortest route inside the shape (checking the three nearest), entering from the nearer end. The first section stays first so start points still work, and an end point keeps the last section last. Travel runs are stitches of up to 2 mm, routed along the edge or the fill rows where they hide.
